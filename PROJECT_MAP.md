# ymoverlay — карта проекта

Маленький Tauri-оверлей поверх YouTube Music в браузере: своё компактное окно
(транспорт, прогресс-бар, очередь, плейлисты), которое управляет реальной
вкладкой music.youtube.com, читая и кликая по её DOM. Никакого API YouTube —
всё через скрапинг и синтетические клики.

## 1. Архитектура в двух словах

Приложение — это **два независимых окна Tauri**, объявленных в
`tauri.conf.json`:

| Окно      | label     | Что грузит                | Видимость            |
|-----------|-----------|----------------------------|-----------------------|
| Основное  | `main`    | реальный `music.youtube.com` | видимое, это и есть YTM |
| Оверлей   | `overlay` | наш `index.html` (React)   | компактное, `alwaysOnTop`, без рамки |

Никакого бэкенда/сервера нет. Вся "интеграция" — это JS-скрипт
(`ytm-watcher.js`), внедрённый в окно `main` один раз при старте, плюс
россыпь одноразовых JS-скриптов, которые окно `overlay` шлёт в `main` через
Rust-команду `ytm_eval` по мере надобности (клик Play, перемотка и т.д.).

```
┌─────────────────────┐   invoke("ytm_eval", {script})   ┌──────────────────────┐
│  overlay (React UI)  │ ────────────────────────────────▶│  main.rs (Tauri/Rust) │
│  src/lib/ytmBridge.js│                                   │  window.eval(script)  │
└─────────────────────┘                                   └───────────┬──────────┘
        ▲                                                              │
        │  window.__TAURI__.event.emit("ytm://...")                   ▼
        │                                                   ┌──────────────────────┐
        └───────────────────────────────────────────────────│  main (music.youtube. │
          listen("ytm://...") в usePlaybackState.js          │  com), ytm-watcher.js │
                                                               │  живёт в этой странице │
                                                               └──────────────────────┘
```

Важно понимать: `ytm-watcher.js` выполняется **в контексте страницы
music.youtube.com**, а не в нашем React-приложении. Это его собственный,
отдельный DOM/window — все `document.querySelector` внутри него смотрят на
разметку YTM, а не на наш оверлей.

## 3. Поток данных

### 3.1 Из YTM в оверлей (события `window.__TAURI__.event.emit`)

Всё эмитится из `ytm-watcher.js`, слушается в `usePlaybackState.js` через
`listen(...)`. Каждое событие эмитится **только при реальном изменении**
(диффинг происходит на стороне `ytm-watcher.js`, до пересечения IPC-границы) —
это специально, чтобы React не перестраивал список очереди дважды в секунду
из-за того, что просто тикнул таймер.

| Событие | Частота | Что несёт | Кто слушает |
|---|---|---|---|
| `ytm://tick` | ~1/сек (плюс сразу при смене трека; мутации бара сами по себе тик не шлют) | `isPlaying`, `currentTime` (трек-относительный!), `duration`, `volume` | обновляет `currentTime`/`duration`/`isPlaying`, разово подхватывает громкость при первом запуске |
| `ytm://track` | только при смене title/artist/art | `title`, `artist`, `art` | обновляет карточку трека, форсит `setVolume` (на случай сброса громкости новым `<video>`) |
| `ytm://queue` | только при изменении списка/активного элемента и только если открыта панель очереди; скан запускается по MutationObserver + страховочно раз в 5 с (см. §4.3) | до 17 строк (см. §4.3) `{id, title, artist, active}` | `QueueList` |
| `ytm://playlists` | по явному запросу (`fetchPlaylists()`), а также авто-обновление, если `playPlaylist` не нашёл строку | до 30 `{id, index, href, title, author}` из сайдбара (обложки плейлистов не читаются и не показываются) | `PlaylistsPanel` |
| `ytm://add-to-playlist-options` | после `addQueueItemToPlaylist()` | `{index, options: [{label}]}` | всплывающий пикер в `QueueRow` |

### 3.2 Из оверлея в YTM (команды через `ytmBridge.js` → `ytm_eval`)

Каждая функция в `ytmBridge.js` строит JS-строку и шлёт её в `main`. Ничего
не выполняется в окне оверлея — только конструирование скрипта.

- **Транспорт (высокая надёжность):** `togglePlay`, `next`, `prev`, `skip(delta)`.
- **Seek (см. §4.2):** `seekTo(target, knownElapsed)` — относительная дельта,
  без доверия к какому-либо закешированному оффсету.
- **Громкость:** `setVolume(percent)` — не пишет `video.volume` напрямую, а
  выставляет *желаемый* уровень, который `ytm-watcher.js` сам непрерывно
  переприменяет (см. §4.4).
- **Очередь:** `selectQueueItem(index)`, `addQueueItemToPlaylist(index)`,
  `confirmAddToPlaylist(label)` — индексы всегда идут через
  `window.__ymoverlay.getQueueItems()`, общий источник истины с
  `readQueue()` (см. §4.1).
- **Плейлисты (см. §4.6):** `fetchPlaylists()`, `playPlaylist(playlist)`.

## 4. Ключевые механизмы и уже закрытые баги

Каждый пункт ниже — это реальная проблема, найденная и исправленная в ходе
работы. Если что-то из этого снова "поедет" при очередном редизайне YTM —
начинать чинить нужно именно с описанного здесь механизма.

### 4.1 DOM-десинхронизация / скрытые и дублирующиеся узлы

YTM рендерит скрытые/дублирующиеся `<ytmusic-player-queue-item>` (офскрин-копии
для анимации) и по два экземпляра title/byline (desktop/mobile-варианты).
Простой `querySelector`/`querySelectorAll` без фильтра ловит не тот узел →
индексы в UI расходятся с реальными DOM-индексами ("кликаю по строке 3,
включается трек 2").

**Фикс:** `window.__ymoverlay.getQueueItems()` и `.firstVisible(root, selector)`
в `ytm-watcher.js` — единственные точки входа для чтения очереди/полей трека,
оба фильтруют через `window.__ymoverlay.isVisible(el)` — это `el.checkVisibility()`
(не форсирует layout), с фолбэком на `offsetParent !== null` для старых webview.
Не заменять на `getBoundingClientRect()`/`getClientRects()`/`offsetParent`
в горячих путях: все три вызывают синхронный layout всей страницы YTM (см. §5),
а `isConnected` видимость не проверяет и вернёт баг с дублями. `readQueue()` и все команды в
`ytmBridge.js` (`selectQueueItem`, меню "..." и т.д.) обязаны ходить через
них, а не писать свой `querySelectorAll`.

### 4.2 Таймер и перемотка: `video.currentTime` — это НЕ секунды в треке

YTM не сбрасывает `<video>.currentTime` между треками очереди — это один
непрерывный счётчик на всю gapless-сессию.

- **Таймер:** `trackStartOffset` в `tick()`/`checkTrackAndTimer()` — в момент
  смены трека запоминает текущее сырое значение как "0" этого трека, дальше
  просто вычитает его из свежего чтения.
- **Перемотка:** `seekTo(targetSeconds, knownElapsedSeconds)` в `ytmBridge.js`
  **не** восстанавливает абсолютное время сессии через `trackStartOffset`
  (закешированное значение может быть устаревшим на момент клика и уводит
  перемотку в чужой трек) — вместо этого считает дельту между желаемой и
  последней подтверждённой позицией (обе в трек-относительной шкале, оффсет
  сокращается) и применяет её к `video.currentTime`, прочитанному свежим тут
  же, — тем же способом, каким уже надёжно работает `skip()`.
- `commitSeek` в `usePlaybackState.js` дополнительно не даёт цели подойти
  ближе `SEEK_END_SAFETY_MARGIN_SECONDS` (1.2с) к концу трека — иначе
  секундная задержка опроса watcher'а может протолкнуть перемотку за границу
  трека, и YTM интерпретирует это как "трек закончился".

### 4.3 Пределы пула очереди (защита от фриза интерфейса)

`getQueueItems()` возвращает вообще все смонтированные строки — YTM их не
анмаунтит, и за долгую сессию/при скролле список может разрастись до сотен.

- `MAX_HISTORY_TRACKS = 6`, `MAX_FORWARD_TRACKS = 10` — что реально
  показывается в UI.
- `MAX_POOL_SIZE = 30` — отдельный, более широкий потолок: сколько сырых DOM-
  узлов `readQueue()` вообще просматривает за тик (окно вокруг активного
  трека), ДО чтения title/byline у каждой строки — именно это, а не лимиты
  показа, реально ограничивает стоимость сканирования.
- **Скан очереди не по таймеру, а по событию** (раздел QUEUE SCAN SCHEDULING в
  `ytm-watcher.js`): `MutationObserver` на контейнере очереди YTM
  (`ytmusic-player-queue`; childList + текст + атрибут `selected`) запрашивает
  скан → запросы склеиваются (`QUEUE_DEBOUNCE_MS` = 200мс) и ограничены одним
  сканом в `QUEUE_MIN_INTERVAL_MS` (1 с — не чаще старого опроса даже при
  шторме мутаций). Страховочный опрос — раз в `QUEUE_SAFETY_TICKS` (5) тиков
  на случай изменений, которых наблюдатель не видит. Пока контейнера нет в DOM
  (`getQueueContainer()` вернул `document`), наблюдатель не вешается.
- **ADAPTIVE BACKOFF** сохранён: если скан занял дольше 80мс, следующий
  разрешён не раньше чем через `ceil(мс/80)` секунд (максимум 10) — одна
  медленная страница даёт редкую паузу, а не стену фризов.
- Всё это гейтится `window.__ymoverlay.queuePanelOpen`: панель очереди в
  оверлее закрыта → наблюдатель отключён, таймер сброшен, сканов нет. При
  открытии (`setQueuePanelOpen(true)` → `onQueuePanelChange`) — немедленный
  скан (см. `setQueuePanelOpen` в `ytmBridge.js` / эффект в
  `usePlaybackState.js`).
- Индекс (`id`) каждой строки — это её **настоящая** позиция в полном
  (неурезанном) списке `getQueueItems()`, а не порядковый номер после
  обрезки: иначе клик по строке снова начал бы попадать не в тот трек.

### 4.4 Принудительное удержание громкости

YTM периодически (~раз в 60с и при каждой смене трека) синхронизирует
`<video>.volume` со своим ВНУТРЕННИМ объектом плеера, затирая любое прямое
присваивание. `applyTargetVolume()` в `ytm-watcher.js` поэтому правит не
только `<video>.volume`, но и сам внутренний плеер (`#movie_player`/
`ytmusic-player`.`setVolume()`), плюс best-effort — `localStorage["yt-player-
volume"]`. Перепроверяется на интервале 200мс (только пока реально играет
звук) и на нативном событии `volumechange`.

### 4.5 Трек-десинхронизация при выборе музыки прямо в UI YTM

Смена трека кликом внутри самого YTM (не через кнопки оверлея) может идти по
более "тяжёлому" пути обновления DOM плеер-бара, чем через очередь. Секундный
опрос иногда попадал ровно на промежуточное состояние и не успевал поймать
момент, когда всё осело.

**Фикс:** `MutationObserver` на `ytmusic-player-bar` (`ensureTrackObserver()`)
— при реальной мутации DOM сразу вызывает `checkTrackAndTimer(true)`
(общую с секундным опросом), а не ждёт следующего тика. Опрос раз в секунду
остался как подстраховка.

Нюансы (оптимизация): (1) записи, затрагивающие только `.time-info` (текст
таймера, меняется раз в секунду), отбрасываются — иначе наблюдатель был
вторым опросом; (2) при вызове из наблюдателя и том же треке `ytm://tick` не
шлётся (его пришлёт опрос), при смене трека — шлётся сразу; (3) наблюдатель
намеренно висит на всём баре, а не на узле заголовка: Polymer может подменить
узел, и наблюдатель на старом узле замолчал бы.

### 4.6 Плейлисты — список из сайдбара; Shuffle без навигации, Play sequentially с навигацией

Раньше при пустом сайдбаре был fallback: реальная навигация скрытого окна на
`/library/playlists` и `history.back()` обратно — пользователь мог увидеть
это как моргание своей видимой вкладки YTM. Полностью убрано.

Разметка подтверждена через девтулз:

```
ytmusic-guide-section-renderer
  #items
    ytmusic-guide-entry-renderer      ← одна строка сайдбара (и нав-пункты, и плейлисты)
      div.title-group                 ← название
      div.subtitle-group              ← автор
      ytmusic-play-button-renderer#play-button
        div.content-wrapper (24×24)   ← круглая Play-кнопка (yt-icon + спиннер)
```

Вся DOM-логика живёт в `ytm-watcher.js`, `ytmBridge.js` лишь запускает её:

- `getSidebarPlaylistEntries()` — обходит **все** `ytmusic-guide-entry-renderer`
  в `#items`. Строка считается плейлистом, если в ней есть Play-кнопка или
  ссылка `a[href*="playlist?list="]` (нав-пункты отсеиваются). Возвращает
  `{el, index, id, href, title, author}`. `id` — `list=…` из ссылки,
  а если ссылки нет — `t:<title>|<author>` (+`#n` для одинаковых строк).
  `index` — позиция в отфильтрованном списке (до `slice(0, 30)`).
- `readPlaylists()` / `emitPlaylists()` — то же без DOM-узлов; `fetchPlaylists()`
  просто вызывает `emitPlaylists()`.
- `playSidebarPlaylist({id, index})` ← `playPlaylist(playlist)` в `ytmBridge.js`:
  находит строку (`resolvePlaylistEntry`: индекс принимается, только если `id`
  на этой позиции совпал; иначе поиск по `id`) → `simulateHover` (pointer/mouse
  over/enter/move) → ждёт Play-кнопку до 800 мс → **один** `.click()` по
  `div.content-wrapper` (или по `ytmusic-play-button-renderer`, если обёртки нет)
  → `simulateHover(false)`. Повторный вызов, пока идёт предыдущий, игнорируется
  (`_playlistBusy`). Если строки уже нет — в консоль `main` пишется warn и
  заново эмитится `ytm://playlists`. Путь «Shuffle» не навигирует; «Play sequentially» — навигирует (см. ниже).
- **Известные ограничения:** синтетический hover не включает CSS `:hover` (только
  JS-слушатели), но `.click()` от него не зависит. Кнопка YTM работает как
  play/pause: клик по уже играющему плейлисту может поставить его на паузу.
  Кнопка Play в строке сайдбара **всегда запускает вперемешку** (подтверждено
  разметкой: `ytmusic-play-button-renderer#play-button.ytmusic-guide-entry-renderer`,
  строка — `tp-yt-paper-item role="link"`). Поэтому:
  - **«Shuffle»** = обычный клик по этой кнопке (как выше).
  - **«Play sequentially»** = `playEntrySequentially()`: клик по самой строке (штатная
    SPA-навигация YTM на страницу плейлиста) → ожидание кнопки Play из шапки
    страницы (`ytmusic-play-button-renderer.ytmusic-responsive-header-renderer`,
    aria-label вида «Відтворити pls»; запасные шапки — detail/editable/immersive)
    → клик по ней (она играет по порядку) → через 1 с `history.back()`.
    `findPlaylistPagePlay(title)` берёт кнопку только если её aria-label содержит
    название плейлиста — так не кликнется устаревшая кнопка предыдущей страницы.
  - Вкладка YTM при этом на секунду показывает страницу плейлиста. Чтобы не
    возвращаться назад: `window.__ymoverlay.returnAfterSequential = false`
    (значение по умолчанию — в `ytm-watcher.js`).
  - Не проверено на других типах страниц (альбомы, миксы, подкасты): у них другая
    шапка, при промахе в консоль `main` пишется warn.
  - Клик по уже играющему плейлисту в сайдбаре работает как play/pause (см. выше).

### 4.7 Pin / Unpin (always-on-top)

`isPinned` в `usePlaybackState.js`, стартует в `true` (совпадает с
`"alwaysOnTop": true` в `tauri.conf.json`). `togglePin()` дергает
`getCurrentWindow().setAlwaysOnTop()`. Требует право
`core:window:allow-set-always-on-top` в `capabilities/default.json`. Кнопка в
`App.jsx` — оранжевая, когда закреплено.

### 4.8 Перетаскивание окна и скролл списков

**С v26 перетаскивание — это `data-tauri-drag-region`, а не CSS
`-webkit-app-region`.** (Подтверждено: в v25 с убранным блюром/`pointer-events`,
но с drag-областями лаги оставались, в v26 — нет.) Раньше корневой `div` был одной огромной drag-областью,
а все кнопки/строки — `no-drag`-«дырками». Chromium обязан отслеживать все эти
прямоугольники (и пересчитывать их при скролле/перерисовке) и передавать хост-окну,
а колесо мыши над такой областью идёт через окно-хозяин, а не сразу в страницу.
Симптом: список «замирает», а потом все накопленные тики колеса прокручиваются
разом, при этом таймер и кадры оверлея идут нормально (то есть JS оверлея жив).

Теперь:

- Ни `titlebar-drag`, ни `no-drag`, ни `-webkit-app-region` в проекте нет.
- Ручки — обычные элементы с атрибутом `data-tauri-drag-region`: рамка окна
  (полосы и углы), корневой div, карточка, блок title/artist, нижняя строка.
  Атрибут срабатывает **только на самом кликнутом элементе** (дети его не
  наследуют), поэтому кнопки, слайдеры и списки просто не имеют атрибута — им
  ничего «отключать» не нужно.
- Нужно право `core:window:allow-start-dragging` в `capabilities/default.json`.
  Если перетаскивание вдруг не работает — сначала смотреть консоль оверлея на
  ошибку прав.
- Двойной клик по ручке пытается развернуть окно (`toggleMaximize`), но права на
  это не выдано, так что ничего не происходит.
- **Правило для новых элементов:** хочешь, чтобы за элемент можно было тащить
  окно — повесь на него (не на родителя) `data-tauri-drag-region`. Ничего для
  скролла делать не нужно.

### 4.9 Плейлисты без обложек

`PlaylistRow` показывает только название и автора. Раньше строка грузила
`<img>` (а при отсутствии обложки — заглушку с `placehold.co`, то есть сетевой
запрос на каждую строку). Теперь `<img>` в строке нет, а `ytm-watcher.js` больше
не читает `img` из сайдбара и не шлёт `art` в `ytm://playlists`.

## 5. Производительность (окно overlay)

- `React.memo` на `QueueList`/`QueueRow`/`PlaylistsPanel`/`PlaylistRow`.
- `queueRef` в `usePlaybackState.js` — `selectTrack` читает из рефа, а не из
  стейта `queue`, чтобы не менять свою ссылку при каждом тике очереди (иначе
  `memo` на строках ломался бы при любом обновлении списка).
- **Убрано в v25 как вероятная причина фризов скролла** (оно ставилось «на глаз»,
  без замеров, и вместе давало обратный эффект): `backdrop-filter` на карточке
  (в прозрачном окне он не видит рабочий стол — эффекта нет, а стоимость
  пересчёта на каждый кадр есть), `.gpu-panel` / `.queue-scroll` с
  `translateZ + will-change`, `.is-scrolling { pointer-events: none }` и
  `.gpu-panel:has(.is-scrolling) { backdrop-filter: none }`. Последние два
  переключались посреди колёсного жеста: Chromium заново хит-тестит и заново
  композитит всю карточку в начале и в конце каждого скролла, а колесо над
  элементом с `pointer-events: none` уходит «под» него. В строках списков
  никаких hover-стилей, для которых это делалось, нет вообще.
- **Ничто в оверлее не связано со скроллом YTM.** Скролл списка оверлея не шлёт
  в YTM ни одной команды; очередь приходит только через `ytm://queue` (≤17 строк,
  см. §4.3), плейлисты — по запросу. Поэтому «отвязывать скролл от YTM» не
  нужно — он уже независим.
- `lib/scrollGate.js` + `mergeList()` в `usePlaybackState.js`: пока список
  скроллится, входящие `ytm://queue` / `ytm://playlists` не применяются, а
  запоминается только последний; применяются через 250 мс после остановки
  скролла. Одинаковый payload — полный no-op (тот же массив, тот же стейт),
  изменилась одна строка — перерисуется только она. Плейлисты, уже
  загруженные один раз, при повторном открытии панели не сменяются на
  «Loading…», а обновляются тихо.
- **Диагностика оверлея** (выкл. по умолчанию): ПКМ по оверлею → Inspect →
  Console → `window.__ovDiag.enable()`. Пишет `scroll response` (время от тика
  колеса до первого scroll-события — это и есть фриз), `wheel latency` (насколько
  поздно колесо дошло до страницы), `long task` и `frame gap` (занят ли сам
  оверлей) и список последних `ytm://…` событий/`ytm_eval` перед каждым фризом.
  Фриз без long task/frame gap = оверлей здоров, ввод задержан ДО страницы
  (окно-хозяин, browser-процесс, общий GPU с окном YTM). `enableDiagnostics()`
  окна `main` про оверлей ничего не знает.

### Производительность `ytm-watcher.js` (окно main)

Замеры на синтетической YTM-подобной странице в headless Chromium (порядок
величин, не точные числа для WebView2):

- Главная цена — не GC (аллокации ничтожны: 0 сборок за 15 с при обычной
  нагрузке), а **document-wide селекторы + принудительный layout** от
  `offsetParent`/`getBoundingClientRect`/`getClientRects` (все три стоят одинаково,
  ~15мс на странице в 36 тыс. узлов после любого изменения стиля).
- Чтение шапки плеера теперь идёт внутри закэшированного `ytmusic-player-bar`
  (`getPlayerBar()`/`barField()`: перерезолв при отсоединении узла или смене
  видимой копии, через `firstVisible` — защита от дублей сохранена):
  3–25 мс → 0,2–0,5 мс за проверку.
- `isVisible()` = `checkVisibility()` (не форсирует layout), см. §4.1.
- Очередь — по событию, см. §4.3. Накладные расходы вотчера при открытой
  панели уменьшились примерно в 2,5–3 раза (4000 строк: с ~5 п.п. до ~1,7 п.п.
  загрузки главного потока; `ytm://tick`+`queue` — с ~2,4 до ~1,2 событий/с).
- Сознательно НЕ делалось: object pooling (нечего пулить, вредно для GC),
  `requestIdleCallback` (не уменьшает работу, нет в WebKit), кэш `<video>`
  (YTM подменяет элемент, выигрыш нулевой), перевод времени трека на
  `timeupdate` (4 Гц = больше IPC; CPU-выигрыша нет).
- **Диагностика фризов** (выключена по умолчанию, нулевая цена): в devtools окна
  `main` выполнить `window.__ymoverlay.enableDiagnostics()` — в консоль пишутся
  длинные задачи (>50мс), дрейф таймера (>300мс) с `document.visibilityState` и
  размер JS-кучи раз в ~30с. Долгая задача = поток заблокирован; дрейф без
  долгой задачи при `hidden` = троттлинг окна; рост кучи = утечка/давление GC.
  Окно оверлея (React, ресайз окна, drag-области) этим не покрывается.

## 6. Хрупкие места (за чем следить в первую очередь)

Всё, что ниже, зависит от закрытой разметки YTM и может отвалиться без
предупреждения при редизайне:

- Селекторы `.title`/`.byline`/`.time-info` в `ytm-watcher.js` (шапка плеера).
- Меню "..." строки / "Добавить в плейлист" в `ytmBridge.js`
  (`findRowMenuButton`, `findAddToPlaylistMenuItem`) — многоязычные текстовые
  словари там только запасной вариант, основной сигнал — иконки.
- Структура сайдбара из §4.6 — если Google переименует
  `ytmusic-guide-entry-renderer` или `#play-button`, парсинг и запуск
  плейлистов сломаются одновременно.

- Контейнер очереди `ytmusic-player-queue` / `#queue-container` (наблюдатель из
  §4.3) и `ytmusic-player-bar` (кэш из §5): если Google их переименует,
  очередь обновляется только страховочным опросом раз в 5 с.
- Не возвращать `-webkit-app-region` / `.no-drag` на карточку или списки: это
  подтверждённая причина «замирания» скролла (см. §4.8). `pointer-events: none`
  на время скролла и `backdrop-filter` тоже не возвращать (см. §5).

Если состояние перестало обновляться — первым делом временно поставьте
`"visible": true` для окна `main` в `tauri.conf.json`, откройте девтулз на
нём и перепроверьте актуальные селекторы (см. SELECTOR NOTE в самом верху
`ytm-watcher.js`).
